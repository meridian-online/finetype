The comment block (which the spec required) shifted the pattern down. Not a defect — the spec's own ac-01 description carries the off-by-comment ambiguity.
**Evidence:** `labels/definitions_finance.yaml:131` (comment block start), `:145` (pattern itself).
**Recommendation:** None — nothing to fix on the implementation side. Future spec authoring may want to reference the type key (`finance.currency.amount.validation.pattern`) rather than a line number that shifts as comments grow.

**Recommendation:** None for iter-4 — the constraint is aspirational and pre-dates this PR. Cleaning up the 16 pre-existing warnings in `column.rs` + `precise_audit.rs` is a separate housekeeping card, not iter-4 scope.

### [INFO] Edge-case coverage on the new alternation
**Category:** test-quality
**Description:** The new alternation `^-?[0-9]+(\.[0-9]+)?([eE][+-]?[0-9]+)?$` accepts forms like `1e6` and `1.5E+10` as `finance.currency.amount`. These are technically valid scientific-notation money values but unusual in real-world money columns. MADR 0078 explicitly accepts this trade-off (composition over invention) — narrowing alternation 4 to a money-shaped sub-pattern would re-introduce drift. iter-3's fixture lock confirms no row-level drift on the 12-dataset corpus.
**Evidence:** `vci4_amount_accepts_bare_decimal` lines 1856–1858; MADR 0078 line 89 ("This decision does not retroactively reshape the taxonomy. It is forward-looking.").
**Recommendation:** None. Documented and tested; the `decimal_number → amount` borrow is intentional.
