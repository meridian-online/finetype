## Findings

### [LOW] SOURCES.md path references changed from .orbit/specs/ to specs/
**Category:** cosmetic
**Description:** The cherry-pick from the v4 branch changed `.orbit/specs/2026-04-20-distilled-data-relabel-7-types/spec.yaml` to `specs/2026-04-20-distilled-data-relabel-7-types/spec.yaml` in SOURCES.md and both loaders. Both paths exist in the repo (.orbit/specs/ and specs/ are both valid), but the canonical convention in this project is `.orbit/specs/`. This is documentation only and has zero functional impact.
**Evidence:** `output/distillation-v4/SOURCES.md` lines 4 and 306. `output/distillation-v4/loaders/{loinc,user_agent}.py` docstrings.
**Recommendation:** Could revert to `.orbit/specs/` for consistency, but not worth blocking.

### [LOW] AC-07 spec wording says "ReLU config has no activation/use_layer_norm fields" but v13 config has them
**Category:** spec-mismatch
**Description:** The spec's AC-07 verification text says "ReLU config has no activation/use_layer_norm fields (defaults to ReLU+BN)" but models/sherlock-v13-config.json already has `"activation": "ReLU"` and `"use_layer_norm": false` on main (since it was added). The implementation is correct -- the configs differ only in those two values -- but the spec's verification wording is inaccurate.
**Evidence:** `git show main:models/sherlock-v13-config.json` shows both fields present.
**Recommendation:** No action needed. Spec wording is stale; implementation is correct.

### [LOW] iso_8601_milliseconds generator has a redundant zero-avoidance pattern
**Category:** code-quality
**Description:** The millis generator for iso_8601_milliseconds first generates `gen_range(0..1000)` then checks if zero and re-rolls. This could simply be `gen_range(1..1000)` as done for iso_microseconds. Functionally identical, just slightly more readable.
**Evidence:** `crates/finetype-core/src/generator.rs` lines ~290-296 (diff context).
**Recommendation:** Minor. Could simplify to `gen_range(1..1000u32)` for consistency with iso_microseconds which uses `gen_range(1..1000000u32)`.

### [INFO] pg_short_offset offset loop allows zero with 20% probability
**Category:** design-note
**Description:** The pg_short_offset generator uses a loop that allows zero offset with 20% probability (`gen_bool(0.2)`). This is intentional -- some PostgreSQL timestamps do have UTC offset -- but worth noting that this means ~20% of generated pg_short_offset values will look like sql_microseconds format (no offset distinction). The comment explains the intent.
**Evidence:** `crates/finetype-core/src/generator.rs` diff lines ~279-283.
**Recommendation:** No change. The 80/20 split is a reasonable trade-off between realism and distinctiveness.
