**Category:** doc-precision
**AC:** ac-12

**Description:** Spec ac-12 verification line specifies the section
must contain *the literal phrase* "ENUM type emission". CHANGELOG.md's
`### Changed` heading reads "**ENUM emission dropped from `validate
--db --table`**" — semantically equivalent, missing the word "type".

**Evidence:**
```
$ grep -c "ENUM type emission" CHANGELOG.md
0
$ grep -c "ENUM emission" CHANGELOG.md
1
```

**Why INFO, not blocking:** the verbatim two-line migration map IS
present (in a fenced code block, exactly as the spec wrote it), the
`TRANSFORM_FAILED` token IS present, and the three `### Changed`
entries cover (a) typed columns, (b) ENUM drop, (c) reject ontology
gain — semantic content of ac-12 is fully satisfied. The single-word
delta is pure spec-literal precision, not a substantive miss.

**Recommendation:** in a future polish pass either tighten the
CHANGELOG heading to read "ENUM type emission dropped" to match spec
literal, or amend ac-12 to "literal phrase 'ENUM emission' or 'ENUM
type emission'". Not load-bearing for merge.

### [INFO] spec.yaml internal inconsistency on TRANSFORM_FAILED column semantics — implementation follows MADR 0071

**Category:** spec-precision
**AC:** ac-03 (verification line) vs `ontology_schema` block (lines 338-350)

**Description:** Two parts of spec.yaml describe `TRANSFORM_FAILED`
reject column semantics in opposite directions:

- **ac-03 verification (lines 86-89):** says
  `error_message=<staging cell value>`,
  `constraint_value=<transform expression literal>`.
- **`ontology_schema` (lines 338-350):** says `constraint_value`
  carries the transform expression literal AND `error_message`
  carries the failing input value (matches ac-03 exactly).

But MADR 0071 (referenced via ac-10) defines the canonical convention
the OPPOSITE way:
- `error_message` carries `"transform_failed: <transform-expr>"` literal
- `constraint_value` carries the failing staging cell text

The implementation matches MADR 0071 (the live architectural
decision). `test_vrp_transform_failure_emits_reject_row` asserts the
implemented convention:
```
constraint_value = "2024-02-30"
error_message    = "transform_failed: strptime(...)::DATE"
```

**Why INFO, not blocking:** ac-10 ratifies MADR 0071, and MADR 0071
explicitly declares the convention. The spec carries both
descriptions; the spec-internal inconsistency is between
ac-03/ontology_schema (description text) and ac-10 (decision-pack
ratification). The implementation chose the decision-pack convention
— the right call. Spec text should be reconciled in the next
revision.

**Recommendation:** edit spec.yaml v1.2 to swap the column
assignments in ac-03 verification AND `ontology_schema` block to
match MADR 0071's documented convention. Or amend MADR 0071 to match
the spec's earlier description (less attractive — the
`transform_failed: <expr>` in `error_message` is more useful for
analysts because they see the transform without joining back to the
schema). Defer to a v0.6.20 spec polish PR.
