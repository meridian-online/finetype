## Headline

Profile now checks its own answers against the data. When the model says "this column is a year" and the values are `5, 9, 12`, profile NULLs the guess to `unknown` instead of shipping a wrong type — but only for the ~69 types a corpus sweep proved safe to veto. For the long tail of rare types it can't yet measure, it flags a low pass-rate as advisory and leaves the prediction standing. That asymmetry — confident NO, cautious everywhere else — is the right shape, and it ships with zero retraining. Default-on, with `--no-validation-veto` to turn it off.

All seven ACs are met. Every deviation from the literal AC wording is a real-world widening or a deliberate standards-conformant narrowing, documented in `notes.jsonl` with evidence, and none breaches the Precision Principle. Independent verification reproduced the implementer's claims.

## AC-by-AC

**ac-01 — widen brittle validations (pattern + co-located bounds together).** Met, with documented real-world extensions beyond the literal AC text:
- `rfc_3339`: colon-less `[+-]\d{4}` offset added alongside `[+-]\d{2}:\d{2}|Z`, plus an optional space separator (`... ?(...)`). The space form is evidence-driven (note 3: dominant corpus shape) — a real widening, not arbitrary acceptance.
- `time.iso`: pattern relaxed to `\.\d{1,9}` (not the AC's `\d{1,6}`), bounds `minLength 10 / maxLength 18`. The 1→9 digit span covers .NET 100ns ticks / nanoseconds (note 5), surfaced by the ac-05 sweep. Still an exact time shape.
- `hms_24h`: optional `(\.\d{1,6})?` fractional part; `minLength 7 / maxLength 15` (AC said "keep minLength 8" — lowered to 7 to admit single-digit hours `8:00:00`, an ac-05-surfaced real form, note 5). The fractional part is bounded `\d{1,6}` so the pattern's max length can't exceed maxLength — this is the residual length divergence ac-04 closed.
- `year`: `^\d{4}(\.0+)?$` tolerates integer-valued floats (`1998.0`), bounds unchanged. Exactly as specified.
- `mdy_12h` correctly DEFERRED with a filed taxonomy follow-up (note 2): the seconds-bearing form is a distinct canonical format whose `%I:%M %p` format_string can't round-trip seconds. Right call.

None of these accepts arbitrary input. Each pattern stays anchored to its type's shape; the looseness on time-component ranges (e.g. `99:99:99`) is pre-existing in the original patterns, not introduced here.

**ac-02 — case-fold enum membership only.** Met and correctly scoped. `compile_schema_parts()` strips `enum` from the jsonschema blob and stores a lower-cased `enum_folded: Option<HashSet<String>>`; membership is checked manually on `value.to_lowercase()` AFTER the jsonschema pattern/length check, so any co-attached `pattern` stays byte-exact on the raw value. Both `is_valid` and `validate` carry the fold. The eval gate (`apply_ydf_validation_gate.py`) mirrors it: `enum_set` lower-cased at compile, `value.lower()` at `passes()`. The byte-exact-pattern guarantee is proven by the still-green `ac07_http_method_case_variants` test and the parity fixture (`country_code 'us'`, `http_method 'gET'` still reject — note 2/4). New unit test `ac02_enum_case_fold` pins the day_of_week/gender folds and the non-member rejections.

**ac-03 — source gender enums to standards.** Met (doc). `gender` → HL7 FHIR AdministrativeGender `[male, female, other, unknown]` with reference link; `gender_code` → ICAO 9303 alpha `M/F/X` + ISO/IEC 5218 numeric `0/1/2/9` with both references; description corrected (previously wrongly listed `O` as valid). One judgment call worth surfacing: the implementer **converted `gender_code` from `^[MFX]$` pattern to an enum** rather than keeping the pattern and adding a numeric variant as the AC's prose suggested. The justification (note 5) is sound — case-insensitivity per ac-02 only flows through the enum fold, not a byte-exact pattern, and the numeric codes needed adding anyway. The `gender` enum narrowing (drops `Non-binary`/`Prefer not to say` → FHIR `other`/`unknown`) REMOVES matches, counter to ac-02's "only ADDS" property; the implementer flagged this and ac-05 confirmed no regression (gender 22.3% → 5.2%). Acceptable.

**ac-04 — runtime/eval parity.** Met. Hidden `finetype validate-value` subcommand backs `scripts/validation_parity.py`, which runs a 16-value fixture (all the AC-pinned rescued values plus length/enum edge cases) through both the live Rust validator and the Python gate and asserts identical pass/fail AND the expected outcome. Re-ran here: 16/16 agree. The subcommand reaches the same `validate_value_for_label`/`CompiledValidator` the profile veto uses, so parity is over the real path.

**ac-05 — before/after false-veto sweep.** Met (observation). `output/false-veto-sweep/report.md` over 1.27M agreement columns: day_of_week 70.2→10.7%, gender 22.3→5.2%, year 32.6→0.4%, time.iso 88.4→2.3%, hms_24h 35.8→0.7%, rfc_3339 93.6→2.6%. Five clear the 10% ceiling; day_of_week's 10.7% residual is documented as CORRECT vetoes (category token "Weekday" / night-compounds both lenses mislabelled), validation-attributable rate ~0% — adding those to the enum WOULD breach the Precision Principle, so leaving them is the right call. Zero previously-clean validations regressed. Artefacts sanitised (counts/rates only, no raw corpus values).

**ac-06 — wire veto into profile.** Met, and the load-bearing concern checks out. **Both classification paths in `main.rs` apply the veto identically** (sibling-context path ~L3896 and per-column path ~L3998): each calls `col_validation_veto` → `evaluate_validation_veto`, then `if vetoed { ("unknown", Some(label)) }`, and threads `final_label` through every downstream lookup (broad_type, categorical collection, output). The HARD veto fires only when `pass_rate < 0.5 AND label ∈ audited_safe`; an unmeasured failing label gets `advisory_low` (flagged, never NULLed) — proven by the `unmeasured_label_failing_is_advisory_not_hard` unit test and the `safe_label_with_failing_values_is_hard_vetoed` counterpart. The allowlist is generated by the sweep and embedded via `include_str!`, so runtime scope can't drift from evidence. Output-shape change stated; default-on with `--no-validation-veto`. JSON emits `validation_pass_rate` whenever applicable, `validation_vetoed`+`vetoed_type` and `validation_advisory_low` only when they fire; plain output annotates `⊘ vetoed:<type>` / `⚠ low-pass (advisory)`.

**ac-07 — MADR.** Met (doc). `.orbit/choices/0091-validation-as-veto-asymmetric-signal.yaml`, status accepted. Captures all three decisions (asymmetric signal → veto ships / YES-disambiguation stays blocked; case-fold scoped to membership; standards-sourcing), names the considered options, and cites the verification.

## Scope notes (not defects — honest limitations, documented)

1. **Widened `rfc_3339` space-form offset and other widened patterns may not round-trip through the `validate` materialisation verb.** Notes 3 and 6 record that `strptime('%Y-%m-%d %H:%M:%S%z')` returns NULL for the space-before-colon-less-offset form, so a value the gate/veto now accepts could still materialise as NULL under `finetype validate`. This spec targets the gate/veto path only; materialisation round-trip is explicitly deferred. Worth a follow-up spec so the two surfaces don't silently disagree on the values this spec just rescued, but it is correctly out of scope here.

2. **`gender` enum narrowing removes prior matches.** Covered by ac-05's no-regression check, but the taxonomy now rejects literal `Non-binary` / `Prefer not to say` strings (they're meant to map to FHIR `other`/`unknown` at the data layer). If real columns carry those literals, they'll now fail validation. The sweep says this is net-positive; flagging it for visibility.
