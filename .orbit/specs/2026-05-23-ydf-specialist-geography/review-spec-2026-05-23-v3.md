## Findings

### [MEDIUM] AC-02's per-column `row_hash` join scheme deferred to extractor docstring — concrete shape is non-trivial and worth pinning

**Category:** missing-requirement
**Pass:** 2
**AC:** ac-02

**Description.** The canonical hasher at `scripts/eval_leakage/__init__.py:72` computes `row_hash(header, value)` — a single hash per `(header, value)` *value pair*. `eval/row_hashes.tsv` (351,505 lines) is a flat per-pair table, and `prepare_multibranch_data.py:2983` filters per-value (`d_leak["values_removed"]`). The geography extract emits one row *per column*, with sample values serialised as a `│`-delimited string field (matching `columns.parquet`'s `sample_values_truncated` shape). The unit mismatch is real and standard — the spec acknowledges it ("joining the per-row hashes into a per-column `row_hash` field — concrete scheme documented in the extractor module docstring").

Deferring the concrete join to the docstring is borderline. Two ways the field could be defined, both defensible, both with different leakage-detection semantics:

- **Per-value-overlap leakage (preferred — matches `prepare_multibranch_data.py` semantics):** For each emitted column, compute the multiset of `row_hash(header, sample_value_i)` over the column's sample values. Drop (or flag) the column if *any* member intersects `eval/row_hashes.tsv`. The per-column `row_hash` field can then be the SHA256 of the sorted concatenated per-value hashes — a deterministic column fingerprint that round-trips for spot-checks.
- **Aggregated-hash leakage:** Compute a single hash over the entire `(header, sorted(unique(sample_values)))` tuple and join against a regenerated per-column eval hash table. This is a cleaner per-column abstraction but requires a *new* per-column eval hash artefact, which the spec does not call for.

The second is incompatible with `eval/row_hashes.tsv` as it stands — the spec implicitly assumes the first via "joins these hashes against `eval/row_hashes.tsv` itself", but the unit mismatch is silent.

**Evidence.**
- `/Users/hugh/github/meridian-online/finetype/scripts/eval_leakage/__init__.py:72` — `row_hash(header, value)` is per-pair.
- `/Users/hugh/github/meridian-online/finetype/eval/row_hashes.tsv` — flat per-pair table, 351,505 rows.
- `/Users/hugh/github/meridian-online/finetype/scripts/prepare_multibranch_data.py:2983–2997` — production filter is per-value.
- `columns.parquet` schema (verified): `sample_values_truncated: string`, `│`-delimited; the extract's `sample_values` will inherit this shape.

**Recommendation.** Add one sentence to ac-02 §3 pinning the per-value-overlap interpretation. Concrete shape:

> The extractor splits each column's `sample_values` on the `│` delimiter, computes `row_hash(header, value)` per value, and joins the per-value hashes against `eval/row_hashes.tsv`. A column is flagged as leaked if any of its per-value hashes appears in the eval table. The emitted per-column `row_hash` field is `sha256(sorted_per_value_hashes joined with NUL)` — a deterministic per-column fingerprint for downstream audit.

This is the smallest change that closes the unit-mismatch question without expanding scope. The author can override in the docstring if a different shape is chosen, but as written, the spec is silent on the choice that determines whether the leakage check actually does what it claims.

## Spot-checks the review specifically asked for

### ac-01: cue-audit TSV mechanism — concrete enough? circular failure mode?

**Concrete:** Yes. The chain is `column.rs → audit_sense_header_cues.py → ydf_extract_cue_audit.tsv → extractor reads at startup → sha256-check against embedded constant`. Each link is a script of well-bounded complexity: `header_hint()` is a single function spanning ~300 lines of `match` arms plus `if h.contains(...)` substring matchers (verified at `crates/finetype-model/src/column.rs:3844` onwards). An audit script can grep the exact-match arms with a tokeniser and enumerate the substring matcher lines from a hand-curated whitelist of conditional shapes. The output schema `(header_cue, sense_type, source_file, source_line)` is well-formed.

**Circular failure mode (`column.rs` changes, audit not re-run):** The spec catches this explicitly: "The extractor errors if … the audit script reports `column.rs` has changed since the TSV was generated." The mechanism it implies is content-hash the relevant section of `column.rs` (or the whole file), embed the hash in the TSV header, and have the extractor invoke the audit script in a check-only mode at startup. The spec doesn't pin the hash mechanism, but it's a small, well-trodden pattern (matches `eval_hash_table_sha256:` in `prepare_multibranch_data.py:2944`).

**Residual risk:** the audit script itself can be wrong (miss a substring matcher arm, mis-classify a regex's output type). That's a code-quality risk addressed at PR review, not a spec-text risk.

**Net:** ac-01 is implementable as written.

### ac-02: row_hash join against eval/row_hashes.tsv — well-defined?

**No, not as written.** This is Finding 1 above (MEDIUM). The unit mismatch (per-value `row_hash` vs per-column extract rows) is the load-bearing question, and the spec defers it to the docstring. The fix is one sentence, but until that sentence lands, two competent implementers would build it two different ways with measurably different leakage semantics.

Acceptable given the architecture; tightening the evidence is optional, not required.
