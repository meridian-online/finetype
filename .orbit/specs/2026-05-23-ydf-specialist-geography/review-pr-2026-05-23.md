## ac-01 — geography extract — IMPLEMENTED

`scripts/extract_ydf_specialist_training_data.py` (401 lines) emits
`eval/gittables/v20_training_candidates/geography.tsv` with exactly the
8-column schema the spec asks for. 1,537 rows survive from 6,590,432
input columns after the documented exclusion cascade.

Circular-precision guard:
- Cue list materialised at `eval/gittables/ydf_extract_cue_audit.tsv`
  with sha256 of `column.rs` recorded in header (line 1) — `extract`
  validates the recorded sha against current `column.rs` at startup
  (extractor lines 110–118) and aborts on drift.
- Exclusion rule (extractor lines 196–212) implements the spec literally:
  short-circuits when `sense_pred.startswith(domain_prefix)` — so an
  in-domain sense prediction (e.g. `geography.address.postal_code`) is
  NEVER excluded by the guard, even when its header matches a cue.
  Verified empirically: 164 rows in the TSV have
  `ydf=geography.address.full_address` and
  `sense=geography.address.postal_code` — the exact m-19 diagnostic
  pattern the spec exists to fix. They survived precisely because the
  guard short-circuits on in-domain sense.
- Guard correctly drops 658 rows recorded in `extract_stats.json`.
- The 24 surviving cross-domain cases (sense non-geography) all have
  headers that don't match a non-geography exact cue — e.g. `ISO code`,
  `Qualifier Code`, `plan`, `coronavirus.1`. Header-driven false
  positives by Sense are not the failure mode here; these are
  legitimate disagreements where YDF's value-pattern read wins.

Path portability: `relativise()` (lines 215–223) resolves under
`$GITTABLES_ROOT`, errors otherwise. TSV row sample confirms all paths
are relative (`beauty_sleep/top_businesses.parquet` style); no absolute
paths leak. Fallback root marker in `holdout_paths.txt` covers the
unset-env case.

## ac-02 — leakage firewall — IMPLEMENTED

Three pieces all present:

1. `eval/datasets/sources.yaml` gains two entries (lines 250–268):
   `repo://eval/gittables/v20_training_candidates/` with `role: train`,
   and `repo://eval/gittables/holdout_paths.txt` with `role: eval`. Both
   carry attribution and the firewall rationale.

   membership; `excluded_holdout: 5` in `geography.extract_stats.json`
   (above the >0 floor; gittables ↔ corpus overlap is data-dependent
   and 5 is reasonable for current corpus state).
3. `from eval_leakage import row_hash` (line 48) imports the canonical
   normaliser. `geography.leakage.json` reports:
   `{overlap_count: 0, dropped_due_to_overlap: 126, eval_hashes_checked: 349665,
   geography_rows_emitted: 1537, domain: "geography"}`. 126 columns
   genuinely dropped — the firewall is catching real overlap, not
   theoretical.

The per-value semantics (any per-value hash collision = drop the whole
column) matches the production filter's per-value semantics at
`prepare_multibranch_data.py:843` (`filter_eval_leakage`), invoked at
lines 3087–3088. Belt-and-braces: even if every extracted row evaded
the in-extractor firewall, the downstream filter would catch it again.

## Findings

### M-1 — `prepare_multibranch_data.py:2983` citation is wrong (LOW)

The extractor module docstring (lines 22–24) pins the per-value
join-scheme decision to "the production filter in
`prepare_multibranch_data.py:2983`". Line 2983 is the
**accounting-negatives** comment, not the leakage filter. The actual
filter lives at line 843 (`filter_eval_leakage`), called from lines
3087–3088. The semantic claim (per-value drop) is correct; only the
line citation is wrong.

This is the cycle-3 carry-forward finding M (row_hash join scheme,
"landable inline"). The decision is documented; the pointer drifted.

**Remediation**: Update extractor docstring line 23 to cite
`prepare_multibranch_data.py:843` (or the `filter_eval_leakage`
function name, more drift-resistant). Trivial follow-up — open as
separate task or roll into next touch.

### M-2 — no unit tests (LOW)

Neither `extract_ydf_specialist_training_data.py` nor
`audit_sense_header_cues.py` has tests. The validation is empirical:
committed output artefacts + sha-pinned reproducibility. For a
single-shot extract pipeline whose output is committed and whose
inputs are sha-pinned, this is acceptable — but if either script
develops over time (e.g. ac-05 adds more per-domain knobs beyond
`domain_prefix`), regression risk grows.

Not blocking. Note for follow-up if the extractor surface expands.
