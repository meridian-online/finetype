### [LOW] `representation.text.word` pattern is "precise" by predicate but semantically permissive
**Category:** heuristic-risk / documented
**Description:** The pattern `^[a-zA-Z0-9]([a-zA-Z0-9\-_]*[a-zA-Z0-9])?$`
lives on `text.word` in the taxonomy and is classified `is_precise=true`
by the new predicate. It admits nearly any short alphanumeric /
hyphen / underscore token — matching the pattern that fires on
`excel_format` and `http_method` values, which is precisely why
those columns now post `text.word` instead of the correct named
types. This is the documented frontier of the predicate (MADR 0059
"Consequences" section acknowledges pattern-parse-based tightening is
future work). Not a regression — progress.md calls it out — but worth
flagging for the next iteration.
**Evidence:** `precise_audit.tsv` row for `representation.text.word` is
`true`; changes.tsv shows excel_format/http_method both land on
`text.word` post-patch.
**Recommendation:** Track as a follow-up card: consider adding the
text.word pattern body to the rejected-pattern set, or add a
minimum-restriction length threshold (e.g. "body must have ≥2
distinct character classes"). Not blocking — out-of-scope per spec
and MADR explicitly defers this.

### [LOW] Guard preserves top-1 on all-empty-values columns
**Category:** edge-case
**Description:** When all values are empty strings, the guard's
`.filter(...).all(validator.is_valid)` evaluates `true` on the empty
iterator, the guard fires, and the function returns None (preserve
current label). Pre-guard, the function would fall through to
`non_empty.len() < 3` and also return None. Net behaviour unchanged
(both paths return None), but the semantic route differs. No eval
column in the expanded manifest exercises this path.
**Evidence:** column.rs:3913-3917; pre-existing fall-through at
column.rs:3935.
**Recommendation:** None required — behaviour-equivalent. Flagged for
awareness.

## Honest Assessment

The implementation executes spec v1.2 cleanly and with unusually
strong evidence preservation. The v1.2 assumption-reversal amendments
(ac-04 reframed from "emits excel_format" to "does not emit
categorical", ac-05 delta-script contract moved to an in-spec
compute_regressions.py) are well-reasoned — the progress.md
"Assumption Reversal" section transparently walks through why the
originally-framed expectation was inconsistent with the discovery's
own findings, and the amendment keeps the spec honest rather than
papering over the miss. The taxonomy audit at ac-01b produces a
diffable TSV with real-pattern anchors wired back into ac-01's unit
tests, which is the right structural answer for a heuristic that
will drift as the taxonomy evolves.

Code changes are narrow and well-placed. `is_precise()` correctly
lives on `Validation` (the HIGH review-spec finding addressed), the
guard is the first branch after the function preamble with clear
commenting and spec references, and the rejected-pattern list
covers the loose cases that motivated the predicate. Tests cover
all four guard branches plus 12+ imprecise-pattern assertions and
4 verbatim real-taxonomy patterns. Zero warnings in finetype-model.
Zero regressions on the full 448-row eval manifest.

Remaining issues are all LOW: 6 new fmt-check diffs to clean up
before merge (30-second fix), a stale verification-command string
in the spec (cosmetic), single-commit MADR transition (process, not
substance), a heuristic-precision ceiling that's already documented
as future work, and one behaviour-equivalent edge case. None blocks
merge.

The excel_format "fix" is honestly framed: the column moves from
`categorical` (wrong) to `text.word` (still wrong, closer to the
column's actual shape). That is the guard's designed effect —
preserving raw top-1, not promotion. The follow-up gap (raw model
never predicts `excel_format`) is a retrain/data-quality problem
correctly scoped out per MADR 0059's Option B (deferred). Ship it.
