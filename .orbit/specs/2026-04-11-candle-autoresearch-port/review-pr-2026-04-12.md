## Exit Condition Assessment

The spec defined three exit conditions:

1. **"Profile eval >=160/190 and model published to HuggingFace"** -- NOT MET. Best was 188/227 (82.8%) on the corrected eval set, which is -5 labels from baseline.

2. **"155 <= score < 160 -- keep model artifact locally, do not publish"** -- The result is a regression, not a marginal improvement. The implementer correctly invoked...

3. **"score < 155 (regression) -- revert and investigate"** -- CORRECTLY APPLIED. The GELU+LN changes are not adopted as defaults. The code is kept behind config flags. Decision 0046 captured the outcome.

The implementer handled exit conditions correctly. The experiment failed on its primary hypothesis but produced valuable knowledge (decision 0046, eval quality audit, data quality discovery about zero-header FTMB).

## Findings

### F1 (Advisory): Training config defaults changed despite GELU+LN rejection

**Location:** `crates/finetype-train/src/multi_branch.rs` lines 1330-1331
**Severity:** Advisory (not blocking)

The `MultiBranchTrainConfig::default()` was changed from `lr: 1e-4, weight_decay: 1e-4`
to `lr: 1e-3, weight_decay: 0.01` (ac-09). These new defaults ship with the PR even
though the GELU+LN experiment that motivated them was rejected.

The LR and weight_decay changes were tested only in combination with GELU+LN. Neither
v8 (lr=1e-3) nor v9 (lr=1e-4) improved profile eval, so there is no evidence that
lr=1e-3 improves ReLU+BN training. The v9 result (lr=1e-4 with GELU+LN regressed
equally) does suggest LR is not the primary factor, but the new defaults have not been
validated for ReLU+BN runs.

**Risk:** Low. The defaults only affect new training runs, not existing model loading.
Anyone starting a new training run will get lr=1e-3 instead of 1e-4, which could
produce different results. The old values can be passed explicitly.

**Recommendation:** Consider reverting to `lr: 1e-4, weight_decay: 1e-4` since the
motivation for the change (GELU+LN experiment) was rejected. Or document that the
new defaults are intentional and why. This is not blocking -- just a loose end.

### F2 (Positive): Eval quality audit is excellent work

The eval-quality-audit.md and associated changes to `matching.rs`, `eval_profile.sql`,
`schema_mapping.yaml`, and `manifest.csv` are a significant improvement to the eval
harness. The audit identified 11 debatable ground truth labels and fixed them with:
- Accepted alternative types (e.g., UPC/EAN, DMY/MDY)
- Interchangeability rules in both Rust and SQL eval code
- Airport name reclassification

This work benefits all future model evaluations, not just the GELU+LN experiment.

### F3 (Positive): Methodical experiment design

Three training runs progressively isolating the architectural effect:
- v8: GELU+LN with aggressive LR (confounded)
- v9: GELU+LN with conservative LR (isolated LR)
- v10: GELU+LN with real headers (isolated architecture)

The root cause analysis in progress.md that identified the zero-header FTMB data issue
was particularly valuable. This is exactly the kind of systematic investigation that
decision 0038 ("strength through simplification") calls for.

### F4 (Positive): Clean code architecture

The `Activation` enum, `MergeNorm` enum, and `BranchWeights.activate()` pattern are
clean abstractions. The `build_branch` closure in both crates reduces repetition.
The backward compatibility via `#[serde(default)]` is correct and well-tested.
Train/inference parity is maintained with identical enum definitions and parallel
code structure.

### F5 (Informational): Large PR surface area

37 files changed, +6336/-119 lines. Most of the volume is in:
- Scripts (overnight training, RunPod infrastructure, eval_pack): ~2400 lines
- Research directory (Python autoresearch code): ~1650 lines
- Eval fixtures (NDJSON datasets): ~50 lines
- Decisions and specs: ~1100 lines

The core Rust changes (the actual port) are modest: ~620 lines across
`finetype-train/src/multi_branch.rs` and `finetype-model/src/multi_branch.rs`,
plus ~120 lines in eval code. The signal-to-noise ratio is fine, but future PRs
could consider splitting infrastructure scripts into separate commits/PRs.
