## What `load` does today

```
finetype load --file <FILE>
    Generate runnable DuckDB CTAS from file profiling
```

Sample output for `ecommerce_orders.csv`:

```sql
-- Generated by FineType (240 types, Sense→Sharpen pipeline)
-- Source: ecommerce_orders.csv (100 rows, 12 columns)
CREATE TABLE ecommerce_orders AS
SELECT
    "order_id",                                            -- representation.identifier.alphanumeric_id
    "customer_email",                                      -- identity.person.email
    strptime("order_date", '%Y-%m-%d')::DATE AS "order_date",  -- datetime.date.iso
    CAST(REGEXP_REPLACE(... "total_price" ...) AS DECIMAL(18,2)) AS "total_price",  -- finance.currency.amount
    ...
FROM read_csv('.../ecommerce_orders.csv', all_varchar=true);

SELECT * FROM ecommerce_orders LIMIT 10;
```

It's a one-shot **CSV → typed DuckDB table** generator. Profiles the
file, picks transforms from the taxonomy, emits SQL, prints to stdout
(or file).

## What changed under it

Two recent shipments changed `load`'s position in the pipeline:

- **`validate` shipped (MADR 0064, PR #46).** Now `validate` reads CSV
  and writes a DuckDB `.db` containing the user's table. It already
  does the "CSV → DuckDB" half of `load`'s job — minus the type
  transforms.
- **The transform contract is mature.** Each taxonomy entry has a
  `transform` field (DDL-injectable SQL expression). 240 types ship
  with one. The DuckDB extension already exposes this via
  `finetype_cast(value)`.

So `load` is now doing two things `validate` + the taxonomy already do
separately:

```
| Step                   | Today's owner       | Could be owned by         |
|------------------------|---------------------|---------------------------|
| Read CSV → staging     | load (read_csv)     | validate (already does it) |
| Apply per-column types | load (inline SQL)   | new transform step         |
| Write to .db           | (none — emits SQL)  | validate (already does it) |
```

## Hugh's proposal: pivot `load` to operate on existing tables

Take an existing DuckDB table — VARCHAR columns, raw imported data —
and apply FineType transforms to convert it to typed columns.

Approximate shape:

```bash
finetype load --db data.db --table orders_raw --output orders_typed
# or in-place:
finetype load --db data.db --table orders --apply
```

Steps:

1. Open the DuckDB; profile the table (sample N rows).
2. Pick transforms from the taxonomy per inferred type.
3. Emit `CREATE TABLE orders_typed AS SELECT <transformed columns>
   FROM orders_raw;` — same SQL shape as today, different source.

## Why this is the right shape now

```
| Pipeline step                         | Verb            | Today | Proposed          |
|---------------------------------------|-----------------|-------|-------------------|
| Discover types + emit JSON Schema     | profile         | yes   | yes               |
| Enforce schema; partition valid/reject | validate       | yes   | yes               |
| Transform raw VARCHAR → typed columns | load (rethought)| no    | yes               |
| One-shot CSV → typed DuckDB           | (currently load)| yes   | derived from chain|
```

The current `load` collapses three steps into one. After `validate`
shipped, that collapse hides behaviour analysts want to control —
"validate first, then transform" is more powerful than "infer-and-load
in one shot, hope nothing breaks."

The new `load` becomes the **third verb in a coherent pipeline**:

```bash
finetype profile  -f raw.csv -o json-schema      # → raw.schema.json
finetype validate    raw.csv raw.schema.json --db data.db --table orders
finetype load     --db data.db --table orders --output orders_typed
```

Each step is composable. Each output is durable. None is a black box.

## What about the one-shot CSV → typed-DuckDB use case?

Today's `finetype load -f file.csv` is convenient. We don't want to
lose it.

Two options:

**A. Keep the one-shot path under a different name or flag.** e.g.,
`finetype load --from-csv file.csv` performs profile + validate +
transform in one go. Effectively a convenience composition.

**B. Drop the convenience; document the chain.** Users who want the
one-shot run a 3-line shell script. Cleaner verbs, slightly more
ceremony. The Meridian pillar "write programs that do one thing and
do it well" leans this direction.

Recommendation: **B**. The chain is short and the steps are honest.
Users who don't want to type three commands can write a wrapper.
Internally we can ship a `scripts/load.sh` that does the chain for
the convenience case.

## Verb naming

Three honest names for the new shape:

- **`load`** (rename / repurpose) — keeps the verb users know. Risk:
  the new behaviour differs enough that scripts depending on the old
  shape break silently. Needs a deprecation cycle.
- **`transform`** — describes the new behaviour exactly. Loses the
  "load" mental model.
- **`cast`** — analogous to SQL `CAST` and `finetype_cast`. Most
  evocative; smallest verb.

If we go ahead, **`cast`** is my pick. It's what the operation actually
does (apply per-column transforms = cast each column to its inferred
type), and it composes nicely:

```bash
finetype profile  -f raw.csv -o json-schema    # → raw.schema.json
finetype validate    raw.csv raw.schema.json --db data.db --table orders
finetype cast     --db data.db --table orders  # → orders_typed
```

`load` becomes deprecated → removed in a release cycle.

## Composition with the validate memo

The `validate-required-flags` memo proposed making `--db`/`--table`
optional on validate (read-only check mode). That stays orthogonal —
when `validate` writes a .db, `cast` consumes it. When `validate` runs
in check-only mode, you don't get a .db and `cast` doesn't apply.

The two flow together:

```bash
# Quick check
finetype validate raw.csv raw.schema.json

# Full pipeline
finetype validate raw.csv raw.schema.json --db data.db --table orders
finetype cast --db data.db --table orders
```

## Implementation sketch

1. Add a new subcommand `Cast` (or repurpose `Load`) accepting
   `--db <PATH> --table <NAME> [--output <NAME>] [--apply]`.
2. Open the DuckDB; profile via `validate_table`-style sampling on
   the existing table (read N rows via duckdb shell-out, same as
   validate's existing pattern).
3. Resolve transforms from the taxonomy per inferred type.
4. Emit `CREATE TABLE <output> AS SELECT <transforms> FROM <source>`
   — same SQL shape as today's `cmd_load`.
5. Stretch goal: support `--schema <path>` to cast against an
   asserted schema (skip inference, take the user's schema as
   ground truth).

The transform SQL generation logic in
`crates/finetype-cli/src/main.rs:cmd_load` (around line 5034 onward
based on grep) is largely reusable. The change is the input source,
not the output projection.

## Composes with the schema/profile memo

The schema/profile memo proposed folding table-mode `schema` into
`profile -o json-schema`. That makes the chain even cleaner:

```bash
finetype profile -f raw.csv -o json-schema --stdout > raw.schema.json
finetype validate raw.csv raw.schema.json --db data.db --table orders
finetype cast --db data.db --table orders
```

Three verbs, three output shapes, full pipeline.
