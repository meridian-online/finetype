## Findings

### [MEDIUM] F1 — AC-06 numerator is 1 column short of literal 97.4% target
**Category:** edge-case
**Description:** The spec's AC-06 target reads "221+/227 (97.4%+ label accuracy)". The eval denominator changed from 227 to 242 during GT correction (spec v1.1, pre-implementation). On the 242-column denominator, 97.4% rounds up to 236/242; the PR ships 235/242 (97.1%). PR body explicitly flags this: "we are one column short of that literal reading."
**Evidence:**
- `specs/2026-04-18-v16-data-audit-retrain/spec.yaml:47` — "Profile eval achieves 221+/227 (97.4%+ label accuracy)"
- `eval/eval_output/report.md:9` — "Profile label accuracy | 235/242 (97.1%)"
- Local reproduction: `FINETYPE_MODEL=models/sherlock-v16 make eval-report` → `Profile: 235/242 (97.1% label, 96.3% domain)`
- PR body "AC-06" paragraph — honest disclosure
**Recommendation:** Accept under the spec's "Net improvement required" clause in the verification field (242→242 with +2 vs v14; all exit_conditions met: "Profile eval >= 221/227 with net improvement over v14"). The 221/227 → 242 mapping is non-trivial; ratification of this reading in decision 0049 (or the merge commit message) would close the interpretive gap cleanly. Not a blocker.

### [LOW] F2 — fiscal_year regression root cause not deeply explained
**Category:** test-gap
**Description:** AC-06's verification requires regressions to be "documented with root cause". The PR and eval report list `datetime_coverage/fiscal_year: predicted=year, expected=fiscal_year, conf=0.50` but do not explain *why* (e.g. synthetic fiscal_year data overlap with year generator, sibling-context ambiguity, etc.). Domain is still correct, and the misclassification is close to the decision boundary (confidence 0.50).
**Evidence:**
- `eval/eval_output/report.md:43` — regression row
- PR body "Column-level change vs v14" block — lists but doesn't explain
- decision 0049 mentions the regression by name but not by mechanism
**Recommendation:** A one-sentence note in the PR body or a follow-up card. Not a blocker — the regression is documented, just not analysed. Given all exit_conditions are met and domain accuracy is preserved, this is a nit.

### [INFO] F3 — Pre-existing fmt/clippy-all-targets warnings on main
**Category:** environment-mismatch
**Description:** `cargo fmt --all -- --check` produces 18 diffs and `cargo clippy --workspace --all-targets` produces 43 warnings. Both counts are IDENTICAL on `main` before this PR's changes — none are introduced here. CLAUDE.md claims "zero warnings"; reality on main is 43 warnings from `--all-targets`. CI only runs `cargo clippy -- -D warnings` (lib-only) which is clean.
**Evidence:**

- feat/v16-retrain: 18 fmt diffs, 43 clippy-all-targets warnings
- `.github/workflows/ci.yml:31` — `cargo clippy -- -D warnings` (no `--all-targets`)
**Recommendation:** Not this PR's problem. Worth a cleanup card before next release to align reality with CLAUDE.md.

## Honest Assessment

This is a tight, well-scoped, well-documented PR that fixes two silent measurement-loop bugs (FINETYPE_MODEL_DIR, `ln -sf`) and ships a genuine +2 improvement on a trustworthy eval denominator. Decision 0049 is exemplary — it explicitly owns a prior failure mode (the "232 > 239" evidence turned out to be v14 vs v14 being re-scored) and documents both the fix and the remaining trade-off (synthetic `swift_bic`/`cpt` overlap with `country_code`/`postal_code`). Tests pass, taxonomy aligns, golden tests pass, no Cargo.toml drift, no stray self-link. The only substantive critique is the literal vs spirit reading of AC-06's "221+/227 (97.4%+)" — the PR body is honest about being 1 column short of the literal percentage but net +2 over the v14 floor, which matches the spec's exit_condition "Profile eval >= 221/227 with net improvement over v14". On balance, approve: the fixed measurement loop is worth more than the 1-column target gap, and the hygiene across commits (scoped, well-titled, decision-backed) is high. Follow-up: a tiny one-liner on *why* fiscal_year regressed would close the only loose end.
