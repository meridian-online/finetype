# status/blood_pressure veto — corpus-honest gate says GO, and it's the first genuine GO the gate has cleared.

**Date:** 2026-06-09
**Candidate:** current `main` (v19 + 0.6.25 fixes) **plus** two labels added to the hard-veto allowlist (`labels/veto_safe.txt`): `datetime.component.periodicity` and `representation.numeric.decimal_number`. Sharpen-layer change only — no model retrain, no `models/default` swap.
**Pass:** 33,250-file stratified sample, 33,007 columns measured, 25.7 min. Candidate parquet: `output/corpus-honest-gate/veto_statusbp_pass/corpus_pass/columns.parquet`.
**Gate verdict:** **GO** — zero triggers, no band fired on any label. Report: `output/corpus-honest-gate/gate_veto-statusbp.json`.

## Why these two were off the allowlist

The allowlist (`labels/veto_safe.txt`) is generated by `scripts/false_veto_sweep.py`: a label earns HARD-veto status only if it was MEASURED non-brittle — ≥ 20 both-lens (sense == ydf) agreement columns and < 10% after-fix false-veto rate. Both labels are **rare-starved**: ydf almost never agrees with sense on them, so the agreement set never reaches 20 columns. `decimal_number` is huge in sense predictions (1.9M corpus columns) but ydf maps decimals elsewhere, so the *agreement* set is tiny. The sweep could not measure them, so it omitted them out of caution — and the omission is exactly why the wrong guesses survived as confident labels (`status`→periodicity, `blood_pressure`→decimal) instead of demoting to `unknown`. The corpus-honest gate is the measurement the both-lens sweep could not make.

## The instrument significance

Per CLAUDE.md the corpus-honest gate is a **proven NO-GO detector** (v22/v23/latdec) but its **GO-precision was unvalidated** — every candidate on disk was a known NO-GO or the degenerate v19-self GO. This is the **first non-trivial candidate to clear the gate with a clean GO** (zero triggers) on a change independently validated by the local eval (status/blood_pressure → 0 rejects, no eval regressions). It is the same demote-to-abstain category as the 0.6.24 patch that drove the oracle-aware band refinement, and it behaves exactly as that refinement predicts. This is the labelled GO outcome the `safety_score` precedent said GO-trust must accrue from — but a single GO is not validation; whether to upgrade the gate's GO status in the decision register is an explicit author call, not asserted here.
