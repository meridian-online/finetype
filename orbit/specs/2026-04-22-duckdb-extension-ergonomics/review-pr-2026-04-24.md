### [LOW] `test_vrp_ac02_required_failure` bypasses `validate_table`

**Category:** test-gap
**Description:** The `required` constraint test calls `map_kind(&ValidationErrorKind::Required { ... })` directly rather than constructing a schema and exercising it through the full `validate_table` pipeline. The code comment acknowledges the structural reason honestly (per-cell JSON-string validation doesn't naturally fire a `Required` kind).
**Evidence:** `crates/finetype-core/src/table_validator.rs` ~line 819 (the `#[test] fn test_vrp_ac02_required_failure` block).
**Recommendation:** Non-blocking. The token mapping is fully exercised, but an optional follow-up could construct an object-shaped validator path to give ac-02's `required` case parity with the other five. The spec's verification text is satisfied (each case exists and asserts the expected token); implementer disclosed the caveat in the code.

## Honest Assessment

This is a well-scoped, well-documented implementation. The v1.1 → v1.2 spec pivot (Scenario A) was driven by an actual spike finding (duckdb-rs 1.4.4 `BindInfo` API gap for table-function catalog access), and the resulting architecture — CLI as the sole caller of `finetype-core::table_validator`, `duckdb` CLI as the materialisation engine — is simpler than the original "new table function" design and preserves the authored-time `x-finetype-*` round-trip that gives the feature its analytical value. All 14 ACs have tests or doc artefacts; the 15-test `vrp_*` grid exceeds the spec's floor; the TEMPORARY-staging RAII story works; and the exit-code grid is covered end-to-end including the `--lenient` override. The two minor caveats (ac-02 `required` test bypasses `validate_table`, and stray legacy-sidecar files in the working tree) are disclosed in-code or outside the changeset, not silent cover-ups. Recommend merge; recommend the follow-up append-scan_id test and `.gitignore` cleanup after, neither blocking.
