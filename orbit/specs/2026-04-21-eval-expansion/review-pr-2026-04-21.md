## Findings

### [HIGH] F-H1: Missing planted-collision unit test for ac-06 / ac-07
**Category:** test-gap
**Description:** Both ACs specify verification as "Unit test: plant a row … confirm the filter removes it / confirm exactly K rows are removed." No such test exists. `grep -r "evalx_ac0" crates scripts tests` returns nothing; `grep -r "plant" scripts crates` returns nothing related to this sprint.
**Evidence:** `scripts/prepare_multibranch_data.py` has no `if __name__ == "__main__": test_…` pattern; no `tests/` file for `eval_leakage`; spec prefix `evalx` (spec.yaml line 286) is not used anywhere.
**Recommendation:** Add `scripts/tests/test_eval_leakage.py` (or Rust equivalent) covering (a) normaliser invariants — CRLF → LF, NFC, trim — (b) plant-and-remove round-trip for `filter_eval_leakage`. Without this, MADR 0056's status-movement criterion ("unit test plants a collision and confirms removal") is not met, even though the MADR is marked `accepted`.

### [HIGH] F-H2: sources.yaml missing 1 of 36 distinct source URLs (ac-08)
**Category:** bug
**Description:** 110 manifest rows reference `repo://eval/datasets/csv/coverage_closure_phase_ab.csv` as their `source_url`. That URL has no entry in `eval/datasets/sources.yaml`. Progress.md claims "every unique source_url … has an entry" but the coverage-closure source was added after the sources.yaml snapshot and not back-filled.
**Evidence:**

$ grep -c "coverage_closure_phase_ab" eval/datasets/sources.yaml    # 0
$ python -c "... # manifest unique source_urls: 36; sources.yaml: 35; missing: 1"

**Recommendation:** Add a 36th entry to `eval/datasets/sources.yaml` for the coverage-closure CSV with role=eval, licence=internal, fetched_date=2026-04-21. Trivial ~5-line addition.

### [HIGH] F-H3: ac-12 missing the previously_covered / newly_covered split
**Category:** test-gap (doc)
**Description:** Spec ac-12 verification requires `report.md` to contain (b) a per-type delta table with a `newly_covered` flag on each row; (c) separate subset scores for previously_covered-only vs newly_covered-only. Neither is present. Progress.md says the flagging is "readable from report.md" but grepping report.md for `previously_covered` / `newly_covered` returns zero matches.
**Evidence:** `grep -n 'previously_covered\|newly_covered' eval/eval_output/report.md` → no match. `grep -n '\bnewly\|\bpreviously' eval/eval_output/report.md` → no match.
**Recommendation:** Add a subset-score stanza to `progress.md` (or a new section of report.md) computing (score on the 242-column pre-closure subset) vs (score on the 110-column closure subset). This is ~10 minutes of work given the per-column results already exist in `eval/eval_output/`.

### [MEDIUM] F-M3: prescreen_results.tsv + triage.md are pre-closure snapshots
**Category:** edge-case (auditability)
**Description:** `eval/prescreen_results.tsv` has 338 data rows; `triage.md` also 338. The current manifest has 448 rows. The coverage-closure rows (110) are explicitly not in triage (argued as "new rows, not replacements") but are also not in the committed prescreen TSV — so a cold reader cannot audit the floor-pass boolean for those 110 newly-minted rows without re-running the script.
**Evidence:** `wc -l eval/prescreen_results.tsv → 339` vs `wc -l eval/datasets/manifest.csv → 449`.
**Recommendation:** Re-run `scripts/prescreen_eval.py` against current manifest and commit the 448-row output (or keep separate files for the 338-row audit snapshot vs the 448-row current-state snapshot). This is not a hard spec violation — ac-01 verification doesn't pin the artefact row count — but it is an auditability gap and the spec framing (constraint #9: "manifest.csv remains the single machine-readable source of truth") expects the downstream artefacts to track it.

### [LOW] F-L1: Coverage-closure columns fail realism floors but count toward ac-05
**Category:** design-tension
**Description:** 110 coverage-closure columns each carry 6 values. Entropy caps at log2(6) ≈ 2.58 bits, so types with 3.0-bit floors automatically fail pass_floors. ac-05 doesn't check floors (only ≥5 values), so the gate passes. MADR 0055 floors are nominally the realism bar; MADR 0057 explicitly says carve-out is a provenance escape hatch but still requires pass_floors. For non-carve-out types in the closure set, this tension is silent: pass_floors=False but counted toward coverage.
**Evidence:** `prescreen_test.tsv` sample: `http_method`, `ip_v4_with_port`, `top_level_domain` coverage-closure rows show `pass_floors=False; shannon_entropy:below min 3.0`.
**Recommendation:** Document this tension explicitly in either the handover or MADR 0057. The honest reading is that Phase B's coverage closure buys the measurability floor but not the realism floor, and Phase C (out of scope) is what closes the realism gap. The decision record should state this directly so v18 training doesn't silently treat these rows as realism-passing.

### [LOW] F-L2: `ontology_schema` field `provenance_status` not persisted
**Category:** spec-prescribed-but-not-implemented
**Description:** Spec's `ontology_schema` lists `provenance_status` as a field with enumerated values. progress.md ac-04 claims every new row has `provenance_status=hand-curated` or `synthetic-necessary`. But manifest.csv has exactly 7 columns (dataset, file_path, column_name, gt_label, source_url, licence, fetched_date) — no `provenance_status` column. Triage.md also does not track it. ac-04 verification text "the corresponding manifest.csv row has provenance_status in {real, hand-curated}" is technically uncheckable against the schema that landed. Since there are 0 replace rows, ac-04 is vacuously satisfied — but the ontology field exists only in prose, not in data.
**Recommendation:** Either (a) add `provenance_status` as an 8th manifest column, (b) track it in triage.md, or (c) amend MADR 0055 to explicitly state the field lives in the carve-out table only (for synthetic-necessary types) and defaults to `real`/`hand-curated` by convention otherwise. Lowest-cost fix is (c).

### [LOW] F-L3: Row hashes skipped 7 manifest rows silently
**Category:** edge-case
**Description:** `compute_row_hashes.py` output log says "7 manifest rows missing" — scanned 441 columns out of 448 manifest rows. These are rows whose referenced file exists but whose `column_name` is not present in that file's header (the loader returns `[]` in that case). These rows are also counted as "covered" by `eval_coverage_check.py` when they fall under rule 3 (coverage-file heuristic) or carve-out. So there is a narrow category — ~7 rows — where the row-hash firewall has zero material to protect against, because no values will ever be extracted. Not a bug per se, but worth surfacing.
**Recommendation:** In `compute_row_hashes.py`, emit the list of 7 skipped (dataset, file_path, column_name) tuples so the next session can audit whether those manifest rows are correct.

## Honest Assessment

The implementation is substantively correct: the three MADRs are written with genuine content (not rubber-stamped), the coverage gate passes cleanly at 240/240, the row-hash firewall is byte-deterministic and wired correctly into the training pipeline with an escape hatch and logging, the manifest schema migration lands without parse regressions (cargo tests green), the consumer inventory caught and patched the bash read-r drift before the schema change shipped, and CLAUDE.md + sweep_v17.sh carry the retrain-block signage. The hard parts of the sprint — shared normaliser, 4→7 column migration, coverage floor with carve-out — are done well.

What holds back an APPROVE is a small cluster of spec-prescribed verifications that were deferred or handled as claims-without-evidence: (F-H1) the planted-collision unit test that MADR 0056 uses as its status-movement criterion does not exist — a verbal "it works" for the leakage firewall is not the same as a test that would catch regressions next sprint; (F-H2) sources.yaml is 1 entry short of manifest.csv, which is exactly the kind of drift the source-role manifest is supposed to prevent; (F-H3) the previously/newly-covered split that ac-12 calls out explicitly is absent from report.md. Each of these is <30 minutes of work and would convert this to a clean approval. None are blocking in the sense of "the leakage firewall is broken" — they are blocking in the sense that the spec's verification text is explicit and has not been met.

The LOW-severity findings (F-L1/2/3) are design tensions worth surfacing for the next session rather than blockers. F-M3's auditability gap is real but not contractual.

The v18 retrain block is honoured by the sweep_v17.sh comment + sprint policy. This review is one of the things guarding that block; approving it as-is would mean accepting that the leakage firewall ships without a round-trip test.
