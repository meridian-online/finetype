## Findings

### [HIGH] F-H1 (CYCLE-2): `sources.yaml` still missing `coverage_closure_phase_ab.csv` entry

**Category:** bug / stated-but-not-done
**Description:** Cycle-1 review raised this as F-H2. Progress.md's detour entry reads *"addressed F-H2 (sources.yaml entry for coverage_closure_phase_ab.csv)"*. But the entry does not exist in the working tree:

```
$ grep -c 'coverage_closure_phase_ab' eval/datasets/sources.yaml
0
$ python3 -c "set(manifest) - set(sources_yaml)"
{'repo://eval/datasets/csv/coverage_closure_phase_ab.csv'}
```

This is the one `source_url` that 110 of 448 manifest rows point at. Spec ac-08 verification is explicit: *"every distinct source_url in manifest.csv … has an entry."* 35/36 is not "every."

**Evidence:**
- `eval/datasets/manifest.csv` lines with `coverage_closure_phase_ab`: 110
- `eval/datasets/sources.yaml` lines with `coverage_closure_phase_ab`: 0
- `grep -cE '^\s*-\s+source_url:' eval/datasets/sources.yaml` → 35

**Recommendation:** Append a 36th entry to `eval/datasets/sources.yaml` following the existing shape:

```yaml
  - source_url: repo://eval/datasets/csv/coverage_closure_phase_ab.csv
    role: eval
    licence: internal
    fetched_date: 2026-04-21
    attribution: "Hand-curated coverage-closure format exemplars (Phase A+B, ac-05). 6 rows each for 110 zero-coverage types. See orbit/decisions/0057-eval-coverage-floor.md."
    datasets: [coverage_closure_phase_ab]
```

Also correct progress.md's detour note — the line claiming F-H2 was addressed is false as landed. Trivial to fix.

**Severity rationale:** HIGH because (a) the spec AC is not met, and (b) progress.md self-reports a fix that didn't ship. The second is worse than the first — it erodes the trust contract progress.md is supposed to enforce.

### [MEDIUM] F-M1 (CYCLE-2): ac-07's "plant K collisions, confirm K removed" verification not literally met

**Category:** test-gap
**Description:** Spec ac-07 verification text: *"Unit test: seed a training corpus with K planted collisions against row_hashes.tsv; run the pipeline and confirm exactly K rows are removed and the log reports K."* The cycle-1 response added `scripts/eval_leakage/test_normaliser.py` — which covers ac-06 normaliser identity but not ac-07's pipeline-level plant-and-remove round-trip. `filter_eval_leakage()` itself has no unit test.

The soft argument is that if the shared normaliser is correct and the filter does `if row_hash(h, v) in eval_hashes: drop`, then correctness is compositional. In practice this is persuasive, but the spec is specific.

**Recommendation:** Add a small test that constructs a `columns_by_type` dict with K planted rows whose (header, value) pairs appear in `eval/row_hashes.tsv`, calls `filter_eval_leakage(columns, eval_hashes, min_values=1)`, and asserts `stats['values_removed'] == K`. ~15 lines of code; closes the spec text literally.

**Severity rationale:** MEDIUM — the composition argument is strong and the normaliser test closes the riskier half. A regression here would be caught by any user actually running a training sweep.

### [MEDIUM] F-M2 (CYCLE-2): `prescreen_results.tsv` still 338 rows vs 448 in manifest

**Category:** auditability
**Description:** Cycle-1 F-M3 carried forward as known-limitation in progress.md. Committed `eval/prescreen_results.tsv` has 338 rows; current manifest has 448. The 110 closure rows were never pre-screened against the formal floors (they wouldn't pass entropy — F-L1 tension).

Not a spec violation (ac-01 doesn't pin the file's row count to current manifest), but the single-source-of-truth constraint (manifest.csv) implies downstream artefacts track it.

**Recommendation:** Re-run `scripts/prescreen_eval.py` against the full 448-row manifest and commit the fresh TSV. Alternatively, explicitly tag it as `prescreen_results_338row_snapshot.tsv` and document both in the handover.

**Severity rationale:** MEDIUM — auditability, not correctness. A cold reader cannot reconstruct the pass_floors booleans for the 110 newly-added rows without re-running the script.

### [LOW] F-L1 (CYCLE-2): Coverage-closure rows fail MADR 0055 entropy floor but count toward ac-05

**Category:** design-tension (documented as known-limitation in progress.md)
**Description:** 110 closure rows have 6 values each; Shannon entropy ≤ log2(6) ≈ 2.58 bits. Many type families floor at 3.0 bits. MADR 0055 is "realism bar"; ac-05 is "coverage floor (≥5 values)". A non-carve-out closure row can pass ac-05 while failing MADR 0055's pass_floors. Handover acknowledges this.

**Recommendation:** None beyond handover tracking. Phase C (out of scope) is the long-term fix.

### [LOW] F-L2 (CYCLE-2): `provenance_status` field enumerated in ontology_schema but not persisted

**Category:** spec-prescribed-but-not-implemented (documented as known-limitation in progress.md)
**Description:** Spec's ontology_schema section lists `provenance_status` as a field with enumerated values {real, hand-curated, synthetic, distilled, synthetic-necessary}. Manifest has 7 cols — no provenance_status column. ac-04 (0 replace rows) is vacuously satisfied, but ac-04's verification text refers to this field as if it existed. F-L2 in progress.md defers this.

**Recommendation:** Either add as 8th manifest col when first `replace` lands, or amend MADR 0055 to state the field lives in the carve-out table only. Lowest-cost fix is the latter.

### [LOW] F-L3 (CYCLE-2): 7 manifest rows produce no hashes silently

**Category:** edge-case (from cycle-1 F-L3, carried forward)
**Description:** `compute_row_hashes.py` log: *"7 manifest rows missing"* — referenced files exist but `column_name` not found in file header. The row-hash firewall has no material to firewall for those columns. Not a bug but worth surfacing.

**Recommendation:** Emit the skipped tuples (dataset, file_path, column_name) to `eval/row_hashes_skipped.tsv` or just to stderr. Next session can audit whether those manifest entries are correct.
