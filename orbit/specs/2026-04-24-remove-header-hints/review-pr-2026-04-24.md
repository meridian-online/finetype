## Findings

### [HIGH] `scripts/rhh/regenerate_all.sh` cannot run on stock macOS bash

**Category:** environment-mismatch
**Description:** The script uses `declare -A pre` (associative array, bash 4+) at line 83. macOS ships bash 3.2.57 at `/bin/bash` (and `/usr/bin/env bash` resolves there by default — the `bash` Homebrew formula is not on a stock dev machine PATH). Reviewer ran `./scripts/rhh/regenerate_all.sh --fast` and got an immediate error.
**Evidence:**
```
$ ./scripts/rhh/regenerate_all.sh --fast
./scripts/rhh/regenerate_all.sh: line 83: declare: -A: invalid option
```
`/bin/bash --version` → 3.2.57(1). `env bash --version` → 3.2.57(1). Verified independently with `bash -c 'declare -A foo'` → same error.
**Why this matters:** ac-09 is a **gate** AC. The reproducibility gate's verification text says "Running `scripts/rhh/regenerate_all.sh` twice in a row on the same machine produces byte-identical output". On the primary dev platform (macOS — see CLAUDE.md "Metal auto-detected on macOS", multiple Metal references) the script does not run at all. The ac-09 *test* (`test_rhh_ac09_*`) passes only because it (a) checks `chmod +x` and (b) compares committed `rhh_fingerprints.sha256` against the on-disk TSVs at rest. It never exercises the regenerate script.
**Recommendation:** One of:
- Switch to a portable construct (parallel arrays, or `case`/`echo` keyed on file path) so the script runs on bash 3.2.
- Update the shebang to `#!/usr/bin/env bash` *and* add a runtime guard `((BASH_VERSINFO[0] >= 4)) || { echo "requires bash 4+, install via brew install bash"; exit 1; }` plus a documented prerequisite in the script header and methodology.
- Rewrite as a Python script (matches the rest of `scripts/rhh/`).

### [MEDIUM] ac-03 schema deviates from spec — measurement invariants no longer checkable

**Category:** spec-drift
**Description:** Spec ac-03 prescribes columns `family_id, columns_hit, columns_correct, columns_wrong, columns_unused` with invariants `columns_hit + columns_unused == 352` and `columns_correct + columns_wrong == columns_hit`. The shipped `diagnostics/rhh_hit_counts.tsv` has columns `family_id, hit_count, measurement_mode, rule_family_class, keep_required, note` — none of `columns_correct`, `columns_wrong`, `columns_unused` exist. The literal verification cannot be evaluated.
**Evidence:** `diagnostics/rhh_hit_counts.tsv` line 5 (schema header), and the spec's ac-03 description block.
**Why this matters:** The spec also says "the sum of columns_hit across families with matching prefix tags equals the count of rows in the baseline profile output whose disambiguation_rule has that prefix (counted independently by `rhh_ac03_totals` test)". That test is also missing.
**Recommendation:** Either (a) extend the TSV schema to include `columns_correct`/`columns_wrong`/`columns_unused` for direct-mode families and document N/A for internal-mode families, or (b) update the spec to match the shipped schema and call out the design pivot in writing on the spec itself (not just progress.md). Add an `rhh_ac03_totals` test.

### [MEDIUM] ac-04 row-count invariant from spec does not hold

**Category:** spec-drift
**Description:** Spec ac-04 verification: "Row count equals sum of columns_hit across all family_ids from ac-03." Sum of `hit_count` in `rhh_hit_counts.tsv` direct-mode families = 11+11+1+40+3+2+1 = 69. `rhh_counterfactual.tsv` has 9856 rows = 22 families × 448 columns. The implementer redefined "hit" via `label_changed == 1` post-disablement (uniform across direct + internal families) and ran every column under every family — defensible and documented in `rhh_methodology.md` "Measurement Approach", but the literal spec invariant fails.
**Evidence:** `diagnostics/rhh_counterfactual.tsv` line count vs `diagnostics/rhh_hit_counts.tsv` summed `hit_count` column.
**Why this matters:** The pivot is a more rigorous measurement (counterfactual surfaces internal-family effects that prefix-match misses). But the spec's open-question 4 (sibling-context interaction) explicitly remained out of scope, and downstream consumers reading the spec literally will mis-interpret what counterfactual rows represent. There is no `rhh_ac04_baseline_match` test (spec named one) that would have surfaced this asymmetry.
**Recommendation:** Update the spec's verification text in a follow-up commit (post-merge OK) to match the implemented uniform-hit definition, OR add the `rhh_ac04_baseline_match` test asserting the actual invariant the implementation does maintain (every counterfactual row's `baseline_label` matches the corresponding row in `eval/eval_output/profile_results.csv`). The spec invariant as written is unrecoverable without reverting the design.

### [MEDIUM] `rhh_family_inventory.tsv` line ranges overlap

**Category:** spec-drift
**Description:** Spec ac-01 verification: "Every (file, line_start, line_end) triple points to real, non-overlapping line ranges in the repo." The shipped inventory has many overlapping ranges:
- `substring_matcher_identity` (4263-4384) and `substring_matcher_technology` (4278-4387) — overlap 4278-4384.
- `substring_matcher_geography` (4291-4338) is fully contained inside identity (4263-4384) and technology (4278-4387).
- `substring_matcher_datetime` (4341-4375) is also inside identity and technology.
- `substring_matcher_finance` (4390-4426) and `substring_matcher_representation` (4404-4460) overlap 4404-4426.
- Branch families nest similarly: `header_hint_hardcoded` (1159-2369) contains `header_hint_cross_domain` (1126-2318), `header_hint_same_category` (1098-2296), and several others.
**Evidence:** `diagnostics/rhh_family_inventory.tsv` lines 7-12 (substring), lines 15-25 (branch).
**Why:** This is genuinely structural — the substring matchers are interleaved arms in a single function rather than per-domain blocks; the branch families are guards inside `apply_header_sharpen` that all live in the same function body. The implementer chose entry-point-anchored ranges, which is the only granularity that matches the rule-family granularity the spec also requires.
**Recommendation:** Either (a) update spec ac-01 to drop the non-overlap assertion (acknowledging that family ranges are entry-point markers, not contiguous code blocks) or (b) record per-family `entry_line` (single line where the disable flag is read) rather than `line_start`/`line_end` ranges. (a) is simpler and matches the actual measurement; (b) is more honest about what the inventory tracks.

### [LOW] ac-09 reproducibility lacks documented seed/determinism flags

**Category:** spec-drift
**Description:** Spec ac-09 verification: "byte-identical holds on the same machine under deterministic inference (seed pinned in the regenerate script, CUDA/Metal determinism flags set where possible)". `regenerate_all.sh` runs the python pipeline scripts in order without setting `PYTHONHASHSEED`, `RHH_DISABLE_HINTS`, any Metal/CUDA determinism env vars, or `--seed` flags. The byte-identical contract holds in practice for ac-01/03/05/06/07 (deterministic Python) but ac-04 (`finetype profile` invocation) has no documented determinism guard.
**Evidence:** `scripts/rhh/regenerate_all.sh` lines 36-150 — only `set -euo pipefail` and `cd "${REPO_ROOT}"`; no env-var pinning.
**Recommendation:** Add `export PYTHONHASHSEED=0` and any documented determinism flags relevant to the multi-branch inference path. If multi-branch is bit-exact regardless, document that fact in the script header so reviewers know the absence is intentional.

## Honest Assessment

This is a substantive, careful piece of measurement work. The instrumentation design is genuinely good — single cfg-gated hook per function entry point, zero-cost when off, family-level granularity matching the runtime emitter, no per-arm sprawl. The artefacts (22 families × full counterfactual on 448 columns, model pinned by sha256, schema-aware label equivalence mirroring eval_profile.sql) reflect more rigour than the spec strictly required. The methodology doc is honest about its limitations (sibling-context not permuted, 80% is policy, no per-arm decomposition). The PR description is well-organised.

The findings cluster around *literal-spec adherence vs intent-spec adherence*. The implementer made several design pivots (uniform `label_changed == 1` hit definition, schema reshape on ac-03, entry-point-anchored line ranges) that are defensible and documented in progress.md and the methodology doc, but they leave the spec's verification text speaking about a different artefact than what shipped. Some spec-named tests are simply missing (`rhh_ac01_inventory`, `rhh_ac03_totals`, `rhh_ac04_baseline_match`, `rhh_ac02_disable_all`).

The **gating** issue is the bash-3.2 break in `regenerate_all.sh`. Because this is a macOS-first codebase and ac-09 is one of two `gate`-typed ACs in the spec, the reproducibility script must run on the primary dev platform without preconditions. Fixing it is a half-hour of shell rewriting (use parallel arrays or rewrite in Python) and unblocks the whole gate.

The other issues are either documented pivots (acceptable to merge with a spec-text follow-up) or low-cost test additions. None of the medium findings invalidate the roadmap conclusions; the per-domain follow-up specs can consume `rhh_roadmap.tsv` as it stands.

**Recommendation:** Fix `regenerate_all.sh` to run on stock macOS bash; add at minimum the `rhh_ac01_inventory` and `rhh_ac04_baseline_match` tests; record the ac-03 schema deviation and ac-04 hit-definition pivot in the spec body (not just progress.md). Once those land, this is APPROVE-ready.
