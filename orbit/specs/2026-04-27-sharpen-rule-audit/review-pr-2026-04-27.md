## Findings

### [LOW] Missing sharpen_audit_verdicts.tsv

**Category:** doc
**Description:** Spec ac-02 verification says "Categorisation recorded in diagnostics/sharpen_audit_verdicts.tsv" but this file does not exist. The verdict data is captured in `progress.md` instead.
**Evidence:** `ls diagnostics/sharpen_audit_verdicts.tsv` returns "No such file or directory"
**Recommendation:** Either create the TSV with columns (rule_id, subsystem, verdict) or accept that progress.md serves the same purpose. Since ac-02 is typed `gate`, this is not blocking.

### [INFO] Gate arithmetic is internally consistent

The score file `diagnostics/v19_cleaned_profile_score.txt` honestly reports that the original MADR 0066 gate FAILS (net_label_delta = -2, needs >= 0). It passes only under the amended gate (MADR 0069), which compares post-cleanup (369) against pre-cleanup candidate score (365), not the v16 baseline (371). MADR 0069 is well-reasoned: removing rules that fight the model is a quality improvement, and the cleaned pipeline outperforms the candidate's own pre-cleanup score by +4. The -2 delta versus v16 baseline is a regression in absolute terms that the project accepts knowingly.

### [INFO] skip_sharpen diagnostic flag added to public struct

The `set_skip_sharpen()` method is `pub` and persists on `ColumnClassifier`. The doc comment correctly notes it is "not part of the public API contract." The hidden `--raw-model` CLI flag gates it with a WARNING to stderr. This is appropriate for diagnostic tooling.

### [INFO] Generator improvements are ancillary

The `generator.rs` changes (wider year ranges, non-zero microseconds, era format variation) are training data quality improvements that shipped as part of the v19 corpus prep. They are harmless and improve format distinctiveness for several datetime subtypes.

### [INFO] TUI scroll fix is unrelated but harmless

The `tui.rs` change (TableState for epoch table scrolling) fixes a UX issue where the epoch table showed the first epochs instead of the latest. Unrelated to the audit but landed on the same branch from the overnight sweep work. No risk.

## Honest Assessment

This is a well-executed audit with clear evidence at every stage. The ablation methodology is sound: profile all 448 manifest rows with and without Sharpen, attribute each change to its rule, compute net impact. Three rules removed (net -2, net -1, net 0) with clean deletion and 9 tests removed alongside. The gate amendment (MADR 0069) is the key decision -- it allows promotion at 369/448 instead of requiring >= 371 (v16 baseline), justified by rule count reduction. The decision is defensible: fewer heuristics + same-or-better-than-candidate accuracy is a real improvement, even though it is 2 labels below the v16 baseline. The project accepts this regression knowingly and documents it honestly. The implementation is clean, the diff is straightforward (deletion, not refactoring), and all tests pass.
