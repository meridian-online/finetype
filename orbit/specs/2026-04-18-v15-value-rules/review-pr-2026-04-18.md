## Approach Assessment

The spec called for 6 value-based rules (R25-R30) to fix 8 columns. The implementation took a fundamentally different approach (Option C from the handover notes): narrowing 7 harmful `header_hint()` keyword matches and adding only 2 value-based rules (R25, R27). This is justified for several reasons:

1. **The handover analysis showed 6 of 8 target columns were harmed by header hints, not by model errors.** Removing the root cause (bad hints) is cleaner than adding compensating rules.
2. **Option C fixes the spec review's blockers (B1, H1) by elimination.** R28 and R29 (email_display, phone_e164) were blocked by header hint overrides. Instead of placing them as post-hint guards, the hint keywords were narrowed so the model's correct predictions survive. R25 was blocked by R12 firing first; it was repositioned as a guard inside R12's postal_code path. R26 and R30 became unnecessary after hint narrowing because the model already predicts correctly.
3. **Net code deletion in the hint system.** The implementation removes 7 keyword matches that actively harmed accuracy, aligning with decision 0042 (remove regex header hints).
4. **The spec review's L1 finding (R27 needs year range check) was incorporated** — R27 checks both 90% 4-digit AND 80% in 1900-2100.

Verdict: **Approach change is justified.** The implementation achieves the spec's intent (fix misclassifications) through a better mechanism (removing root causes vs. adding compensating code).

## Findings

### [OK] R25 HTTP Status Guard — Correctly Placed

R25 was placed as a guard inside `disambiguate_numeric()` at line 4694, inside the `consistent_digits && typical_postal_range && !is_sequential` block, after the year check. This directly addresses the spec review's H1 finding (R25 was dead code if placed after R12). By positioning R25 inside R12's postal_code detection path, it intercepts the exact decision point where HTTP status codes would be misclassified as postal codes. When the guard fires (3-digit, >=90% in 100-599), it returns `None` instead of postal_code, preserving the model's original `integer_number` prediction.

### [OK] R27 Year Gate — Year Range Check Incorporated

R27 at line 2811 checks `compact_ym` predictions with two thresholds: >=90% of values are exactly 4 digits, AND >=80% of those 4-digit values fall in 1900-2100. This addresses the spec review's L1 finding. The `u16` parse rejects negative numbers and values >65535. "0000" parses as 0, outside 1900-2100, so it won't trigger. Empty/whitespace values are filtered by `!v.is_empty()` after `trim()`. Minimum 3 non-empty values required.

### [OK] R25 Empty Value Handling

`disambiguate_numeric` parses values via `v.trim().parse::<i64>()` (line 4590), filtering out empty strings, whitespace, and non-numeric values. Requires `parsed.len() >= 3` (line 4593). Mixed 3-digit/5-digit values: `digit_lengths` would have inconsistent lengths, so `digit_lengths.iter().all(|&l| l == 3)` returns false, and R25 never fires. The postal_code detection also requires `consistent_digits`, so mixed-length columns bypass the entire block.

### [OK] R27 Edge Cases — "0000" and Negative Numbers

"0000" has `v.len() == 4` and parses as `u16(0)`, but `(1900..=2100).contains(&0)` is false, so it does not count as a year candidate. Negative numbers like "-200" fail the `v.chars().all(|c| c.is_ascii_digit())` check (dash is not a digit), so they don't count as 4-digit values. Both edge cases are handled correctly.

### [OK] Keyword Guards — No Major Unintended Consequences

Tested scenarios:
- `email_display_name` -> normalized to "email display name" -> contains "display" -> guard blocks email hint -> model decides. Correct — this is a display name column, not an email column.
- `display_email` -> contains "display" -> guard blocks. Acceptable — ambiguous header, model should decide.
- `phone_e164_formatted` -> contains "e164" -> guard blocks. Correct.
- `hotel` -> contains "tel" -> still matches phone hint. Pre-existing issue, not introduced by v15.

### [MEDIUM] M1: IP "port" Guard May Over-Block

The guard `!h.contains("port")` on the IP keyword match (line 4111) blocks any header containing the substring "port". This includes "import_ip" (normalized: "import ip"), "transport_ip", "airport_ip", etc. These headers would match the IP pattern ("import ip" ends with " ip") but also contain "port" (from "import"), preventing the ip_v4 hint.

**Evidence:** No current eval datasets have such headers (searched `eval/schema_mapping.yaml`). The risk is theoretical.

**Mitigation:** The guard could be tightened to `!h.contains("with port")` or `!h.contains("_port")` (pre-normalization) to only block the specific `ip_v4_with_port` pattern. However, this is low priority given no practical impact and the existing IP exact-match block covers common cases ("ip", "ip address", "server ip", etc.).

## Test Adequacy

**Strengths:**
- 3 tests for R25 covering positive (status codes), negative (5-digit postals), and boundary (3-digit non-HTTP postals)
- 3 tests for R27 covering positive (years), negative preservation (6-digit compact_ym), and false positive rejection (non-year 4-digit)
- 6 tests for keyword guards covering both the guard (blocked) and the pass-through (still matches) for each change
- Tests exercise `value_sharpen()` and `header_hint()` directly, which is appropriate for unit-level validation

**Gaps:**
- No integration test exercises the full `classify_multi_branch` pipeline end-to-end for the keyword guard changes. The spec review's B1 finding (header hints override value_sharpen) was the motivation for Option C, but there's no test proving the keyword narrowing prevents the override. The eval report serves as the integration test, but it's not automated in CI.
- The `ac01_r25_http_status_gate_fires_on_status_codes` test uses `if let Some` on the result (line 6207), meaning it passes vacuously if `value_sharpen` returns `None`. In practice, R12 fires and the guard returns `None`, so the test does pass correctly (no postal_code returned), but the assertion structure could be tighter — asserting `result.is_none()` would be clearer.

These gaps are acceptable given the eval report validates the full pipeline, and the test count is already at 407 (+24 from baseline).

## Verdict: PASS

The implementation takes a cleaner approach than the spec prescribed. Instead of 6 compensating rules, it removes 7 root causes (harmful keyword matches) and adds 2 rules where the model genuinely cannot distinguish (HTTP status vs postal code, year vs compact_ym). The approach:

- Fixes all spec review blockers (B1, H1) by elimination
- Achieves 218/227 (96.0%), up from 215/227 (94.7%), with 0 regressions
- Net code deletion in hints, small additions for rules
- All 407 tests pass
- Decision 0048 followed (value-based rules only)
- Edge cases in R25 and R27 handled correctly

The one medium finding (IP "port" guard over-blocking) has no current practical impact and can be tightened if a real-world header like "import_ip" is encountered.
