## Findings

### [HIGH] LOC delta misses spec target by ~195 lines

**Category:** spec-gap / partial-AC
**AC:** ac-05
**Description:** Spec ac-05 binds `crates/finetype-cli/src/main.rs` net
LOC delta to `≤ -250 measured against PR #54's post-merge HEAD (the
schema-verb-fold parent)`. The verification command in the spec is
`git diff --stat rally/schema-verb-fold..HEAD -- crates/finetype-cli/src/main.rs`
showing net ≤ -250.

**Evidence:**

```
$ git diff --shortstat rally/schema-verb-fold..rally/validate-absorbs-load -- crates/finetype-cli/src/main.rs
 1 file changed, 374 insertions(+), 429 deletions(-)
$ # Net delta = 374 - 429 = -55 LOC, NOT ≤ -250.
$ # main.rs line count: 5142 (parent) → 5087 (head) = -55.
```

`progress.md` line 11 claims `LOC delta -420 (well under -250 target)`.
That figure measures *gross deletion of cmd_load + helpers* in
isolation, not the net main.rs delta the spec requires. The implementer
added back ~340 LOC of in-file unit tests (5 functions in the existing
`#[cfg(test)] mod tests` block) and rewrote `cmd_validate_table`'s
materialise path with the projection wiring + pre-CTAS
transform-failure sweep, soaking up the deletion budget.

**Why this matters:** The constraint exists to validate the
hard-removal posture is honest and not papered-over. Spec carries
explicit numeric ACs precisely so the rally pipeline can audit them
without judgement calls. The ≤ -250 line was set deliberately (the
implementer's interview noted ~270 LOC for cmd_load alone), and a -55
delta materially misses it.

**Recommendation:** Either:
1. **Cleanly satisfy** by relocating the 5 `build_transform_projection_*`
   unit tests from `main.rs`'s `tests` module into a new
   `crates/finetype-cli/tests/build_transform_projection.rs` integration
   test file. Estimated impact: -130 LOC out of main.rs, pushing the net
   to roughly -185. Then move the long `cmd_validate_table` typed-projection
   and pre-CTAS-sweep helper into a sibling module
   (`crates/finetype-cli/src/validate_materialise.rs`) — straightforward
   refactor, no behaviour change. Combined this clears -250 with margin.
2. **Amend** spec.yaml v1.2 with revised ac-05 wording — e.g.
   `≤ -250 LOC measured as the sum of cmd_load + build_load_expr +
   build_load_expr_enum + sanitise_identifier function bodies removed,
   excluding new test-module additions.` Re-run review-spec then
   re-issue review-pr.

Either path shows the LOC contract was understood and honoured. Today's
diff demonstrates neither.

**Description:** ac-08 verification line 201 says

**Why this is LOW, not blocking:** the file's pre-existing convention

violated, but the policy intent (don't disable tests by accident) is
honoured.

**Recommendation:** clarify ac-08 to read "No `#[ignore]` annotations
that disable test execution from `make ci`" — or accept the existing
file-level convention as authoritative. Either way, no behavioural
change is required.

## Honest Assessment

This is a clean, well-engineered implementation of every behavioural
acceptance criterion the spec lists. The 13 ACs are honestly attempted
and all functional and qualitative requirements pass:
`build_transform_projection` is testable in isolation with five clean
branches, the pre-CTAS sweep correctly distinguishes NULL-in-NULL-out
from genuine transform failures (ac-04 evidence is unambiguous),
`finetype load` is hard-removed via clap's stock unknown-subcommand
handler (no shim, no warning, exit 2), the reject ontology extends
cleanly with `TRANSFORM_FAILED`/`transform`, MADR 0071 is thoroughly
written including the `error_message` semantic split that cycle-1
review-spec called out, and `make ci` is green end-to-end. 13/13
testable ACs have verification evidence; clippy and fmt are clean
under the strict gates the spec demands.

The single substantive issue is the LOC contract on ac-05: the spec
sets `≤ -250` against PR #54's HEAD, the implementation lands at -55.
The implementer's hand-off note (`progress.md`) reports `-420` but
that figure is gross deletion of `cmd_load` + helpers measured in
isolation, not the net main.rs delta the spec specifies and that the
verification command (`git diff --stat`) computes. The deletion is
real — it's just been re-spent inside main.rs on (a) five unit tests
that could trivially live in a `tests/` integration file, and (b) a
materialise path that grew a non-trivial pre-CTAS sweep. Both
expansions are legitimate code; neither belongs against the deletion
budget the spec set.

Two tractable paths forward: relocate the in-file unit tests (and
optionally the materialise helper) into sibling files to clear the
-250 numerically, OR amend the spec with the actual measurement basis
the implementer has been using and re-run review-spec → review-pr. I'm
not in a position to choose between them — both are honest. What I
can't do is APPROVE while a numeric AC misses by 195 LOC.

Findings 2 and 3 are minor and do not on their own block merge. The
LOC delta does, until either the implementation or the spec aligns.
