### [MEDIUM] F1 — AC-06 floor gate has 98 fails (not 0); deferral acceptable but verification-text untouched
**Category:** spec-violation / pragmatic-deferral
**Description:** AC-06's verification block requires `awk -F'\t' 'NR>1 && $14=="False"' /tmp/validate_corpus_iter2_prescreen.tsv | wc -l` to return 0. Actual count is 98 across 10/12 datasets. The cycle-1 fix (commit `5d47505`) appended a "Pre-screen floor deferral (AC-06 gap-downgrade)" section to `eval/eval_output/validate_corpus.md` (lines 151–183) explaining the 4 dominant causes (SDMX flat-dimensions, CODE/LABEL pair design, "88+2" composite ratings, real-world 2-3-value categoricals) and why constraint #5's drop-and-replace is not satisfiable for these patterns. The reasoning is sound — replacement would forfeit the mechanism coverage that motivates dataset selection. Floor recalibration is identified as unfiled future work.

**However**, AC-06 itself was not amended in spec.yaml (constraint #9: "no new MADRs"; spec is also frozen). AC-06's pinned shell still says "→ 0" while the actual is 98. The spec text and the shipped state disagree.

**Evidence:**

**Recommendation:** ACCEPT the gap-downgrade. The deferral is now visible in the report (cycle-1 addressed the cycle-1 reviewer's main objection), the structural reasoning is sound, and replacement-vs-retain is a real design tension. Iter-3 / iter-4 follow-up should either:
1. Add a `validate-real-world` floor profile distinct from the synthetic-generator profile, or

Either is mechanism-orthogonal to iter-3's attribution-rule scope (already filed).

Not blocking for this PR — the destructive re-run pattern only fires if a future implementer re-runs the harness without restoring from git, which is unlikely during normal iter-3 work (iter-3 will modify the harness and re-emit).
